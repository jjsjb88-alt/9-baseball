## 0. 왜 이전 기획안으로 부족한가 — 자기 반박

이전 판(부록 A)은 **텍스트 113개를 28개로 줄인다**가 결론이었다. 그건 **증상 처치**다.

세 가지가 빠져 있었다.

1. **텍스트가 많은 게 병이 아니라, 모든 요소가 똑같이 시끄러운 게 병이다.**
   위계가 없으면 20개로 줄여도 20개가 동시에 소리친다.
2. **읽을 수 없는 크기로 쓰여 있다.** 11px 미만 글자 선언이 **433곳**이다(§1.2).
   안 읽는 게 아니라 **못 읽는다.** 글자를 지우기 전에 남길 글자를 읽히게 만들어야 한다.
3. **디자인 시스템이 없다.** 색 리터럴 2106개 / 토큰 11개, `!important` 2266개,
   z-index 51종, 브레이크포인트 24종(§1). 이 상태에서 화면을 고치면
   **다음 세션이 다시 무너뜨린다.** 규칙 없이 고친 화면은 마스터피스가 아니라 다음 회귀다.

따라서 이 문서는 순서를 바꾼다.

> **시스템(§3) → 구조(§4) → 언어(§5) → 부품(§6) → 문법(§7~9) → 치환(§10)**

## 1. 감사 — 현재 상태 실측

재현 명령은 부록 B에 있다. 대상: `src/duel/*.css` 21개 파일 5258줄.

### 1.0 실측 — 렌더된 화면 (신규)

정적 grep이 아니라 **실제 빌드를 Chromium 390×844에서 조작해** 얻은 값이다.
경로: 타이틀 → `새 런 시작` → 1막 정규 승부 → `스윙하기` → 카드 3장을 9존에 배치.
캡처는 `docs/design/v12/`에 있다.

| 측정 | 값 | 판정 |
| --- | ---: | --- |
| 보이는 텍스트 노드 | **211** | 정적 추정(113)의 **1.9배** |
| 그중 11px 미만 | **186 (88%)** | — |
| 최소 글자 크기 | **5.5px** | 한글 자소 붕괴 |
| 12px 이상 | 25개 (12%) | 읽히는 글자가 8분의 1 |

### 1.0.1 블록 좌표 — 이것이 "복잡함"의 물리적 실체

| 블록 | y | 높이 |
| --- | ---: | ---: |
| 전광판 | 84 | 62 |
| **투수 HP** | **152** | 54 |
| 경기장 | 212 | 287 |
| **9존 보드** | **505** | 364 |
| 배치 가이드(HP ×0.79) | 559 | 150 |
| 스윙 드로어 | 964 | 548 |
| **손패** | **1063** | 182 |

- 9존(505~869)을 보는 스크롤 위치에서 **투수 HP(y152)는 화면 밖**이다.
  → 카드를 놓으면서 그 결과인 HP를 **볼 수 없다.**
- 9존 하단(869)과 손패 상단(1063) 사이 **194px**. 뷰포트 844 안에 둘이 **동시에 들어오지 않는다.**
  → 카드를 보려면 내리고, 존을 보려면 올린다. **한 번의 배치마다 스크롤 왕복.**

**§13 결정 1(투수 HP를 보드 위로)은 선택이 아니라 필수다.** 현재 위치에서는
어떤 고스트 표시도 보이지 않는다.

### 1.0.2 감사에서 놓쳤던 것 — 9존 셀 안의 텍스트

정적 감사에는 없었다. 실제 화면의 셀 하나에 텍스트가 **3~4개**씩 있다.

```
┌──────────────┐
│   IN · HIGH  │  ← 위치명
│     LOW      │  ← 확률 등급
│    비숙련     │  ← 숙련도
└──────────────┘
```

9칸 × 3~4 = **약 30개**가 보드 안에만 있다. 여기에 배치 토큰(`1 섬타 노림 ↔`)이 더해진다.

### 1.0.3 실제 렌더 버그 3건

캡처에서 확인된 것이며, 이 기획과 별개로 **이미 깨져 있다.**

| # | 증상 | 캡처 |
| --- | --- | --- |
| 1 | 배치 토큰이 셀 경계를 넘어 **옆 칸 글자를 덮는다**(`…림` 잘림) | `before-portrait-390.png` |
| 2 | **가로모드에서 좌하단 블록이 서로 겹친다** — `BATTLE READOUT`·`SWING`·`COVER`·`COACH`가 한 자리에 포개짐. 카드가 하단에서 잘림 | `before-landscape-844.png` |
| 3 | 세로모드 우하단 `선수는 베이스에 · 카드는 행동에`가 **화면 밖으로 잘림** | `before-portrait-390.png` |

2번은 §1.1의 `!important` 2266개가 만든 결과의 **눈에 보이는 증거**다.

### 1.0.4 대비는 문제가 아니었다 — 크기가 문제다

실사용 색 조합의 대비비를 계산했다.

| 조합 | 대비 | 판정 |
| --- | ---: | --- |
| `#F4ECD8` on `#07120F` | 16.18:1 | AAA |
| `#CCD8D0` on `#07120F` | 12.97:1 | AAA |
| `#FFE4A2` on `#07120F` | 15.30:1 | AAA |
| `#7D9388` on `#07120F` | 5.81:1 | AA |
| `#536761` on `#07120F` | **3.16:1** | **본문 실패** |

**5건 중 4건이 통과한다.** 즉 이 화면이 안 읽히는 이유는 대비가 아니라
**6~10px이라는 크기**다. 이전 판이 대비를 의심한 것은 틀렸다.

### 1.1 스타일 시스템 부재

| 지표 | 값 | 판정 |
| --- | ---: | --- |
| CSS 파일 | 21개 / 5258줄 | 같은 화면을 **21개 파일이 동시에 조작**한다 |
| `!important` 총 occurrences | **2266** | — |
| `!important` 포함 줄 | 1024줄 (**전체의 19.5%**) | 5줄에 1줄이 우선순위 싸움 |
| `sts-battleboard.css` | 543줄 중 370 `!important` (**68%**) | 이 파일은 **다른 파일을 이기려고** 존재한다 |
| `landscape-declutter.css` | 336줄 / 175 | 가로모드 전용 override 층 |
| `responsive-master.css` | 161줄 / 104 | 반응형 전용 override 층 |

**해석**: 레이어 설계가 없어서, 새 기능마다 새 CSS 파일이 `!important`로 앞 파일을 덮었다.
화면이 복잡해 보이는 이유의 상당 부분이 **의도된 디자인이 아니라 덮어쓰기의 잔해**다.

### 1.2 타이포그래피 붕괴 — 가장 심각

| 지표 | 값 | 기준 | 판정 |
| --- | ---: | --- | --- |
| 서로 다른 `font-size` 값 | **60종** | 스케일 6~8단 | **실패** |
| 11px 미만 선언 | **433곳 / 16개 파일** | 모바일 최소 12px | **실패** |
| 최소값 | **5.5px · 5.8px · 6.2px · 6.3px · 6.5px** | — | **읽기 불가** |
| `letter-spacing` 선언 | 130곳 | 한글 본문 0 | **확인 필요** |

**해석**: 이 화면의 정보 대부분이 **6~10px 한글**로 적혀 있다.
390px 폭 기기에서 6px 한글은 자소가 뭉개진다. 테스터가 "복잡하다"고 말한 것은
**정보량**이 아니라 **판독 불가능한 밀도**일 가능성이 높다.

한글은 자소 조합이라 라틴보다 큰 하한이 필요하다. 라틴 10px ≒ 한글 12~13px.
여기에 `letter-spacing`을 양수로 주면 음절 블록이 흩어져 더 나빠진다.

### 1.3 레이어 부재

| 지표 | 값 |
| --- | --- |
| 서로 다른 `z-index` | **51종** |
| 범위 | `-2` ~ **9999** |
| 관측값 | 0,1,2,…,14,18,24,30,42,55,80,120,160,9999 |

이름 없는 숫자 51개. 새 요소를 얹을 때마다 "일단 더 큰 수"를 쓴 흔적이다.

### 1.4 색

| 지표 | 값 |
| --- | ---: |
| 색 리터럴(hex/rgb/rgba) | **2106종** |
| 정의된 CSS 커스텀 속성 | **11개** |

팔레트가 없다. 같은 "강조색"이 화면마다 미세하게 다르다.
색으로 의미를 구분할 수 없는 이유가 여기 있다 — **색이 2106개면 색은 의미가 아니다.**

### 1.5 반응형

| 지표 | 값 |
| --- | --- |
| `@media` 폭 분기점 | **17종** (360·380·430·520·560·640·699·700·720·760·800·900·1080·1099·1100·1280·1500) |
| `@media` 높이 분기점 | **7종** (350·380·430·470·650·760·800) |
| 같은 뜻의 중복 | `699/700`, `1099/1100` 동시 존재 |
| `prefers-reduced-motion` 표기 | 공백 있는 판/없는 판 **2종 혼용**(41곳) |

### 1.6 모션

| 지표 | 값 | 판정 |
| --- | ---: | --- |
| `@keyframes` | **176개** | 안무가 아니라 개별 효과의 더미 |
| `animation` 선언 | 228 | |
| `transition` 선언 | 72 | 상태 전환보다 자동 재생이 3배 |
| 서로 다른 이징 | **53종** | 물리 법칙이 53개 |

**해석**: 연출이 호평받은 것은 사실이나, 그것은 **판정 순간의 큰 효과** 덕이다.
UI 상태 전환(선택·배치·순서변경)은 이징 53종이 제각각이라 **같은 세계의 움직임으로 느껴지지 않는다.**

### 1.7 터치 타겟

| 관측된 `min-height` | 개수 |
| --- | ---: |
| 44px | 11 |
| 48px | 10 |
| 52px | 8 |
| **38px 이하** | **38 이상** (38·34·30·28·26px 구간) |

Apple HIG 44pt / Material 48dp 기준 미달 타겟이 다수다. 특히 순서 변경 버튼, 칩, 마이크로 라벨.

### 1.8 감사 결론

| 병 | 증상으로 보이던 것 |
| --- | --- |
| 위계 없음 | "복잡하다" |
| 6~10px 한글 | "못 읽겠다" → "어렵다" |
| 토큰 없음(색 2106) | "정신없다" |
| 레이어 없음(!important 2266) | 화면마다 다른 규칙처럼 보임 |
| 이징 53종 | 조작감이 매번 다름 |

**텍스트 개수는 다섯 번째 문제다.** 위 넷을 고치지 않고 텍스트만 지우면 조용하지만 여전히 읽히지 않는 화면이 된다.

## 2. 마스터피스 판정 기준

"예쁘다"가 아니다. 아래 5개를 **측정**으로 통과해야 한다.

| # | 기준 | 측정 |
| --- | --- | --- |
| 1 | **1초 안에 무엇을 결정하는 화면인지 안다** | 첫 진입자 5명 중 4명이 "지금 뭘 고르는 화면?"에 정답 |
| 2 | **모든 글자가 읽힌다** | 12px 미만 0곳, 본문 대비 4.5:1 이상 |
| 3 | **내 선택의 결과가 한 곳에서 보인다** | 같은 값의 중복 표기 0 |
| 4 | **조작감이 하나다** | 이징 3종 이하, duration 6단 이하 |
| 5 | **다음 세션이 부술 수 없다** | 신규 `!important`·literal 색·12px 미만을 **테스트가 막는다** |

기준 5가 핵심이다. **규격을 문서가 아니라 테스트로 고정한다.**

### 2.1 인지 모델 (설계 근거)

| 법칙 | 이 화면에 적용 |
| --- | --- |
| Miller 4±1 | 한 순간 동시 비교 대상 **4개 이하**. 현재 스윙 화면은 10개 이상 |
| Hick–Hyman | 선택지가 늘면 결정 시간이 로그로 증가 → 행동 3버튼은 유지하되 **동시에 보이는 옵션**을 줄인다 |
| Fitts | 반복 조작(존 탭·카드)은 **크고 가까이**. 9존 셀 ≥ 48×48, 엄지 영역 안 |
| Gestalt 근접성 | **원인과 결과는 붙여 놓는다** — 9존 보드와 예상 피해 바를 한 블록으로(§4.3) |
| 지각 지연 | 시각 피드백 **≤100ms**, 상태 전환 ≤180ms, 연출 ≤700ms |

## 3. 디자인 시스템 — 토큰

**신설 파일 `src/duel/tokens.css`.** 이후 모든 신규·수정 스타일은 토큰만 사용한다.

### 3.1 타입 스케일 (8단 · 모바일 기준)

| 토큰 | 크기/행간 | 용도 | 비고 |
| --- | --- | --- | --- |
| `--t-display` | 40 / 44 | 판정어(안타·삼진) | 1화면 1회 |
| `--t-h1` | 28 / 34 | 화면 제목 | |
| `--t-h2` | 22 / 28 | 블록 제목 | |
| `--t-h3` | 18 / 24 | 카드 이름 | |
| `--t-body` | 15 / 22 | 본문 | 한글 행간 1.45 하한 |
| `--t-label` | 13 / 18 | 라벨 | |
| `--t-micro` | **12 / 16** | **절대 하한** | 이보다 작은 글자 금지 |
| `--t-num` | 20 / 24 | 수치 | `font-variant-numeric: tabular-nums` |

규칙
- **12px 미만 금지.** 기존 433곳은 12px로 올리거나 **글자를 없앤다**(§10). 축소는 해법이 아니다.
- 한글 본문 `letter-spacing: 0`. 제목만 `-0.01em`까지 허용. **양수 트래킹 금지.**
- 숫자는 항상 `tabular-nums` — 값이 바뀔 때 폭이 흔들리면 "정신없음"의 원인이 된다.

### 3.7 이관 전략 — `!important` 2266개를 어떻게 없애나

한 번에 못 고친다. **CSS Cascade Layers**로 구조를 먼저 만든다.

```css
@layer reset, base, field, board, hud, overlay, responsive, motion;
```

1. `tokens.css` + `@layer` 선언 파일을 최상단에 추가한다.
2. 새 규칙은 **반드시 레이어 안에** 쓴다. 레이어 순서가 우선순위를 만들므로 `!important`가 필요 없다.
3. 기존 파일은 통째로 레이어에 감싸 넣는다(내용 수정 없이 `@layer` 래핑만).
   래핑만으로 `landscape-declutter` / `responsive-master`의 override 상당수가 **자연 우선순위**로 정리된다.
4. `!important` 비율이 가장 높은 `sts-battleboard.css`(68%)부터 실제 감축에 들어간다.
5. **신규 `!important` 0** — lint 테스트로 고정(§12.3).

목표: P0 종료 시 2266 → 1200 이하, P4 종료 시 300 이하. **0을 목표로 하지 않는다**(현실적이지 않다).

### 4.1 한 투구는 3막이다

## 5. 시각 언어

개념 7개 = 물체 7개. 각 물체는 **형태·색·움직임 3채널 중 2개 이상**으로 상태를 말한다.

### 5.1 커버 = 켜진 칸

| 상태 | 형태 | 색 | 움직임 |
| --- | --- | --- | --- |
| 미선택 | 얇은 테두리 | `--dim` | — |
| 가능(힌트) | 테두리 유지 + 모서리 마커 | `--aim` 20% | 0.42s 1회 펄스 |
| 메인 커버 | **실선 2px** | `--cover-main` | 점등 0.18s |
| 지원 커버 | **점선 1px** | `--cover-support` | 점등 0.18s |
| 투수 미사용 | **격자 질감 + 눌림** | `--dim` | 없음 |

`COVER 5/9` 숫자는 **칸을 세면 나온다.** 삭제.

### 5.2 위력 = 예상 피해 고스트 ★ 단일 지주

```
투수 HP
[■■■■■■■■■■■■■■■■■■■■□□□□□□□]
                  └▨▨▨▨┘         예상 피해 (반투명 + 45° 해치)
                       └⋰⋰┘      정확 적중 시 추가분 (점선 테두리)
```

| 사건 | 고스트 반응 | 부수 |
| --- | --- | --- |
| 카드 1장 추가 | 길이 **감소** (`--d-state`) | 커버 칸 증가 |
| 이어치기 성립 | 길이 **증가** + 끝단 0.42s 섬광 | 아크 연결 |
| 이어치기 끊김 | 길이 감소 + 끝단 1회 흔들림 | 아크 파열 |
| 메인 정확 적중 카드 | 점선 구간 추가 표시 | 메인 토큰 조준 링 |

**대체하는 표기 30개**: `PRESSURE 80% HP`·보조문(3), `HP POWER`/`HP ×0.80`/`FULL POWER`/`COVER +1 · 위력 -20%`(4),
1~4장 배율 스트립(12), `BASE`/`+`/`CONNECT`/`=`/`FINAL`(8), `PRECISION MAIN` 블록(3).

접근성: 고스트 구간은 `aria-label`로 **정확한 수치 문장**을 계속 제공한다(시각만 지운다).

### 5.3 이어치기 = 배트 궤적 아크

| 상태 | 형태 | 색 | 움직임 |
| --- | --- | --- | --- |
| 이어짐 | **끊김 없는 아크**, 굵기 일정 | `--link-on` | 진행 방향 스윕 0.26s |
| 끊김 | **가시적 틈 + 끝단 파편 3px** | `--link-off`(탈채도) | 1회 흔들림 0.18s |
| 미리보기(순서 변경 중) | 반투명 아크 | `--link-on` 50% | 실시간 재그리기 |

`CONNECTED`/`BREAK`/`1 → 2`/존 이름 **전부 삭제.** 틈은 정지 화면에서도 보인다 → reduced-motion 안전.

### 5.4 순서 = 토큰 ①②③④

숫자 기호는 언어가 아니므로 **유지**. 카드 이름표·`MAIN SWING`·`SUPPORT`·존 부제는 삭제.
토큰 크기 28px, 터치 시 44px 히트 영역.

### 5.5 카드 = 글리프 + 아이콘 1줄

| 유지 | 대체 | 상세로 이동(길게 누르기) |
| --- | --- | --- |
| 이름(`--t-h3`) | 커버 3×3 글리프 | 규칙 설명문 |
| | 역할 아이콘 1 | 강화 설명문 |
| | gives/needs 아이콘 칩 | 플레이버 |
| | 연계=실선 발광 / 상충=빗금 테두리 | |

**1장당 텍스트 9행 → 1행.**

### 5.6 읽기 = 9존 해치 셰이딩

등급 0 = 거친 해치 / 2 = 중간 / 4 = 정밀 + 수치(길게 누르기).

## 7. 인터랙션 문법

### 7.1 제스처 표 · 임계값 · 충돌 해결

| 제스처 | 임계값 | 동작 | 취소 |
| --- | --- | --- | --- |
| 탭 | < 200ms, 이동 < 8px | 선택 / 배치 | — |
| 길게 누르기 | ≥ 400ms, 이동 < 8px | 상세 시트 | 손 떼기 전 8px 이동 시 드래그로 승격 |
| 드래그 | 이동 ≥ 8px | 카드→존 배치, 순서 이동 | 보드 밖 드롭 → 260ms 원위치 복귀 |
| 가로 스와이프(손패) | 이동 ≥ 12px, 각도 < 30° | 손패 스크롤 | |

**우선순위: 드래그 > 길게 누르기 > 탭.** 동시 판정 시 위가 이긴다.

### 7.2 되돌리기

- 스윙 확정 **전까지 모든 배치는 취소 가능**(토큰 재탭 = 회수).
- 확정 후 취소 불가 — 확정 버튼은 **2단(무장→확정)**으로 오조작을 막는다.
- 취소·회수에 확인 대화상자를 쓰지 않는다.

### 7.3 피드백 3중 (모든 입력 ≤100ms)

| 사건 | 시각 | 햅틱 | 사운드 |
| --- | --- | --- | --- |
| 카드 무장 | 12% 확대 + 존 `hint` | 8ms | 픽(2.8kHz) |
| 배치 성공 | 셀 임팩트 + 고스트 갱신 | 18ms | 나무 탁(2kHz) |
| 배치 불가 | 셀 흔들림 | 40ms | 덜컥(저역 뮤트) |
| 이어짐 성립 | 아크 연결 + 고스트 증가 | `[9,18,9]` | 상승 2음 |
| 끊김 | 아크 파열 | 40ms | 하강 1음 |
| 순서 교체 | 아크 재구성 | 12ms | 짧은 스윕 |
| 회수 | 토큰 복귀 | 8ms | 역재생 픽 |
| 스윙 확정 | 보드 잠금 + 필드 전환 | 24ms | 기존 연출 인계 |

사운드 규칙: **UI음은 2~4kHz, -18dB 이하.** 판정 연출의 저역 임팩트와 주파수대를 분리해
동시에 나도 서로를 가리지 않게 한다. `audio.js` 실패가 전투를 막지 않는 기존 계약 유지.

## 8. 모션 안무

### 8.1 공간 모델

**모든 움직임은 출발점을 가진다.** 카드는 손패에서 나와 존으로 간다(페이드 인 금지).
회수는 정확히 역경로. 순서 교체는 토큰이 **서로를 지나가며** 자리를 바꾼다(순간 이동 금지).

### 8.2 스태거

동시에 3개 이상이 변할 때 40ms 간격으로 지연. 예: 커버 칸 5개 점등 = 0/40/80/120/160ms.
**한꺼번에 켜면 "번쩍"으로 읽히고, 순차면 "퍼짐"으로 읽힌다.**

### 8.3 공유 요소 전환

드로어를 열 때 선택된 카드는 **같은 DOM 요소가 이동**하는 것처럼 보여야 한다(위치·크기 보간).

### 8.4 reduced-motion

| 표현 | 대체 |
| --- | --- |
| 고스트 길이 변화 | 즉시 최종 길이 |
| 아크 스윕 | 정적 아크(틈은 유지) |
| 스태거 점등 | 동시 점등 |
| 데모(§11) | 정지 3컷, 탭으로 넘김 |

**움직임이 유일한 전달 수단인 표현은 불합격**(§5의 3채널표로 검증).

## 11. 무언 온보딩

문장이 아니라 **데모 모션**. 투어(텍스트 6장)는 폐기.

| 구간 | 길이 | 화면 | 텍스트 |
| --- | ---: | --- | ---: |
| 1 | 0.6s | 9존 한 칸 펄스 → 고스트 손가락이 탭 | 0 |
| 2 | 0.7s | 손패 카드 1장이 떠올라 그 칸으로 이동 → 커버 점등 | 0 |
| 3 | 0.5s | 예상 피해 고스트가 차오름 | 0 |
| 4 | — | 고스트 손 소멸, 실제 손패가 같은 동작을 대기 | 0 |

- 아무 곳이나 탭하면 스킵. 2타석부터 재생 안 함. 기존 저장은 완료로 간주.
- **첫 공 결과를 조작하지 않는다.** 데모는 *조작 방법*을 가르치지 *결과*를 가르치지 않는다.
- 개념별 1회 데모(겹쳐치기 / 이어치기 / 순서 변경)로 `b.turn<=2` 시간 게이트를 대체한다.

## 13. 아스트라 결정 필요

> **0. 시각 방향을 A / B / C 중에서 고른다**(§17.4). 이 결정이 §4~§6 전체를 확정한다.
> 나머지 항목은 방향이 정해진 뒤에 의미가 있다.


1. ~~투수 HP 바를 9존 보드 위로 내릴 것인가~~ → **실측으로 결론이 났다**(§1.0.1).
   현재 HP(y152)는 9존 조작 중 화면 밖이다. 내리지 않으면 예상 피해 고스트가 **보이지 않는다.**
   남은 질문은 "내릴지"가 아니라 "상단 전광판에 HP를 얼마나 남길지"다.
2. **수치를 0으로 밀 것인가, 상세 시트에만 남길 것인가**(§5.2). 현재 초안은 후자.
3. **카드 이름까지 지울 것인가.** 현재 유지. 아이콘만으로 13종 구분 가능 여부 미검증.
4. **`!important` 감축 목표치**(P0 1200 / P4 300)가 현실적인가. 레이어 래핑만으로 얼마나 빠질지 미측정.
5. **영어 장식 라벨 19종 전면 삭제가 과한가.** 톤이 밋밋해질 수 있다는 반론 가능.
6. **범위**: 보상·시설·지도 화면은 이번 대상이 아니다. 전투만 정리되면 톤이 어긋난다. 이어서 할지.
7. **아트 루프와의 순서.** `HANDOFF.md` 최우선은 여전히 VISUAL REBOOT다. 이 문서는 그 기준을 취소하지 않는다.
8. 표본은 **테스터 1명**이다. §1 감사 수치는 사실이지만, §2 기준 1(5명 중 4명)은 아직 검증 수단이 없다.

### 17.1 시안이 실제로 증명한 것

같은 게임 상태(카드 3장 배치, 1→2 이어짐, 2→3 끊김)를 규격대로 그렸을 때:

| --- | ---: | ---: |
| 보이는 텍스트 노드 | 211 | **16** |
| 11px 미만 | 186 (88%) | **0** (최소 12px) |
| 문서 높이 / 뷰포트 | 1646 / 844 = 1.95 | **844 / 844 = 1.00** |
| 배경색 / 글자색 종류 | 59 / 50 | **16 / 7** |
| HP 효율 표기 | 3곳 | **1곳, 숫자 0개** |
| 투수 HP ↔ 9존 | 한 화면 밖 | **맞닿음** |
| 9존 ↔ 손패 | 194px 떨어짐 + 화면 밖 | **72px, 동시 시야** |

**텍스트 16개는 목표치 28의 절반이다.** 예산에 여유가 있으므로,
검수에서 "너무 말이 없다"고 판단되면 **되돌릴 여지가 있다**(§13-2).

### 17.4 3방향 시안 (2026-09-22 추가)

§17.1의 1차 시안은 **정리는 됐으나 디자인이 아니었다**. 9존이 야구가 아니라 설정 화면 격자였고,
픽셀아트 경기장 위에 플랫 UI 패널이 떠 있었으며(AGENTS §6 "환경 통합" 위반), HP 고스트는
"단일 지주"라 해놓고 화면에서 가장 작고 안 중요해 보이는 18px 막대였다.

그래서 **방향 자체를 3개로 벌려 다시 그렸다.** 같은 게임 상태(카드 3장 · ①→② 이어짐 · ②→③ 끊김),
같은 토큰, 같은 시각 언어. 다른 것은 **세계관**이다.

| 파일 | 방향 | 한 줄 |
| --- | --- | --- |
| `three-directions.png` | **비교 시트** | 3방향 + 평가 + 기준표 |
| `dir-a.png` / `dir-a.html` | **A · 타자 시점(다이제틱)** | 9존이 투수 앞 공간에 선다. HP는 마운드 위 빛의 고리 |
| `dir-b.png` / `dir-b.html` | **B · 전광판(브로드캐스트)** | 화면 전체가 하나의 야구 전광판. 읽기 등급 = 전구 밝기 |
| `dir-c.png` / `dir-c.html` | **C · 덱 테이블(장르 정석)** | 상대 위·보드 중앙·카드 아래. 배치는 칩 |
| `tokens.css` | 공통 토큰 | 세 시안이 공유 |

#### 평가

| 기준 | A 타자 시점 | B 전광판 | C 덱 테이블 |
| --- | :---: | :---: | :---: |
| 야구 정체성 | ★★★ | ★★ | ★ |
| 초보 즉시 이해 | ★★ | ★★★ | ★★ |
| 장르(덱빌딩) 관습 | ★ | ★ | ★★★ |
| 9칸 좌표 비교 정확도 | ★ | ★★★ | ★★★ |
| 기존 아트 의존도 | 높음 | 낮음 | 중간 |
| 구현 난도 | 상 | 하 | 중 |
| 기존 판정 VFX 재사용 | 그대로 | 재설계 필요 | 축소 |
| 텍스트 / 12px 미만 | 15 / 0 | 15 / 0 | 15 / 0 |

- **A**는 야구를 가장 잘 말하지만 **원근 때문에 9칸 크기가 달라 보여 좌표 비교가 흔들린다.**
  그리고 기존 픽셀아트 품질에 가장 크게 의존한다 — 타자 대역 문제가 그대로 노출된다.
- **B**는 전구 밝기 하나로 읽기 등급 3단을 표현해 **가장 직관적이고 구현이 가장 싸다.**
  대신 경기장과 선수가 창 하나로 축소돼 **야구 경기를 한다는 실감이 약하다.**
- **C**는 이 장르 플레이어가 설명 없이 아는 배치지만 **야구가 가장 약하다.**
  투수가 경기하는 상대가 아니라 초상화가 된다.

#### 혼합 가능성

세 방향은 배타적이지 않다. 예를 들어 **B의 전구 격자를 A의 원근 평면에 올리면**
읽기 등급의 직관성과 야구 공간감을 동시에 가져갈 수 있다. 다만 구현 난도는 A보다 높다.
**혼합을 먼저 정하지 말고, 한 방향을 고른 뒤 부족한 축을 보강하는 순서를 권한다.**

#### 여전한 한계

- 정지 1장이다. 이 기획의 절반인 모션(§8)은 **세 시안 어느 것도 증명하지 못한다.**
- **타자/투수 아트 품질은 세 시안 어느 것으로도 해결되지 않는다.** `HANDOFF.md`의
  VISUAL REBOOT 기준은 그대로 유효하다. A는 오히려 그 기준 충족을 **전제로** 한다.
- 가로모드(844×390) 시안은 아직 없다.
- 사람이 어느 쪽을 더 잘 이해하는지는 **검증되지 않았다.** 별 개수는 설계 판단이지 측정값이 아니다.

### 17.3 1차 시안의 한계 — 과장하지 않는다

- **정지 화면 1장이다.** 이 기획의 절반은 모션(§8)인데 시안은 그것을 증명하지 못한다.
- 타자·투수는 **저장소의 기존 스프라이트**를 그대로 썼다. `HANDOFF.md`의 아트 품질 기준
  (타자/투수 비율·밀도 일치)은 **이 시안으로 충족되지 않는다.** 시안에서도 두 캐릭터의
  팔레트와 밀도가 서로 다르다는 것이 그대로 보인다.
- 현재 빌드의 타자는 **배트와 홈플레이트만 있는 대역**이다(`before-portrait-390.png`).
  시안은 기존 스프라이트를 되살려 놓은 것이며, 아트 리부트를 대신하지 않는다.
- 가로모드 시안은 아직 없다. §1.0.3-2의 붕괴는 재설계 대상이다.
- **사람이 이 시안을 실제로 이해하는지는 검증되지 않았다.** 측정된 것은 텍스트 수와 좌표뿐이다.
