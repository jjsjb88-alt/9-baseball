## 0. 이 문서가 앞선 문서들과 다른 점

| 판 | 범위 | 한계 |
| --- | --- | --- |
| 1판 | 온보딩 | 텍스트를 **더** 쓰는 방향 |
| 2판 | 전투 화면 텍스트 | 증상 처치 |
| 3판 | 전투 화면 + 디자인 시스템 | **전투 화면만.** 지도·보상·시설·덱·카드 본문은 손대지 않음 |
| 4판 시안 | 전투 화면 3방향 | 화면 하나의 세계관 선택 |
| **5판 (이 문서)** | **제품 전체** | — |

3판까지의 공통 결함: **범위를 전투 화면으로 좁게 잡았다.**
플레이어는 전투만 하지 않는다. 지도에서 고르고, 보상에서 비교하고, 시설에서 결정하고,
덱을 들여다본다. 그 화면들이 전부 **글자 덩어리**인 한, 전투만 조용해지면 게임은 더 이상해진다.

그리고 더 근본적인 질문을 피했다.

> **"정타 노림"이라는 글자가 정말 필요한가?**

이 문서는 그 질문을 **모든 글자에 대해** 던지고 답한다.

## 1. 제품 문장과 마스터피스 정의

### 1.1 제품 문장 (변경 없음)

> 투수의 의도를 읽고, 9존 위에 카드를 순서대로 배치해 하나의 스윙을 설계하고,
> 투수를 무너뜨리는 야구 덱빌딩 로그라이트.

**게임 방식은 바꾸지 않는다.** 확률·피해·카드 효과·런 구조 전부 그대로다.

### 1.2 마스터피스 판정 — 제품 전체 기준 7개

| # | 기준 | 측정 |
| --- | --- | --- |

| 2 | **모든 글자가 읽힌다** | 12px 미만 0, 본문 대비 4.5:1 |
| 3 | **화면마다 무엇을 결정하는지 1초 안에 안다** | 5명 중 4명 정답 |

| 7 | **다음 세션이 부술 수 없다** | 위 전부를 테스트가 막는다 |

## 2. 근본 원리 — 규칙을 **물리**로 번역한다

지금까지의 접근은 "글자를 아이콘으로 바꾼다"였다. 그건 치환일 뿐 번역이 아니다.
아이콘도 결국 **배워야 하는 기호**다.

마스터피스의 방법은 다르다.

> **규칙을 비유가 아니라 물리로 옮긴다. 물리는 배우지 않아도 이미 안다.**

### 2.1 다섯 개의 물리 번역 — 이 기획의 척추

#### 번역 1. 커버 = 카드가 존을 **덮는다**

카드의 **물리적 형태가 곧 커버 범위**다.

| `shape` (기존 데이터) | 카드 형태 | 예 |
| --- | --- | --- |
| `point` | 작은 정사각 (1칸 크기) | 정타 노림 · 당겨 넘기기 · 끝장 승부 |
| `column` | 세로로 긴 카드 (1×3) | 밀어치기 · 라인드라이브 |
| `row` | 가로로 납작한 카드 (3×1) | 주자 연결 · 갭 공략 |
| `cross` | 십자 형태 카드 | 커트 스윙 · 존 봉쇄 |
| `all` | 9칸 전체 크기 | 희생 번트 |

카드를 존에 올리면 **그 카드가 실제로 그 칸들을 덮는다.**
`COVER 5/9`라는 표기가 필요 없어지는 게 아니라, **존재할 이유가 사라진다.**
덮인 칸은 카드에 가려서 안 보이기 때문이다.

> 이것이 이 기획에서 가장 중요한 한 줄이다.
> `shape`는 **이미 엔진에 있는 필드**다. 새 규칙이 아니라 **있는 규칙을 눈에 보이게** 하는 것이다.

#### 번역 2. 여러 장 = **겹쳐 쌓인다**, 두께가 손해다

카드를 2장, 3장 놓으면 보드 위에 **물리적으로 겹쳐 쌓인다.**
쌓인 더미가 두꺼워질수록 **투수 HP의 예상 피해 구간이 눈앞에서 짧아진다.**

"카드를 더 놓으면 커버는 넓어지고 HP 위력은 내려갑니다"라는 문장이
**쌓이는 동작 하나**로 대체된다.

#### 번역 3. 이어치기 = 카드끼리 **맞닿는다**

인접한 존에 놓인 카드는 **모서리가 붙어 하나의 덩어리**가 된다. 접합선이 빛난다.
인접하지 않으면 **떨어져 있다.** 그냥 떨어져 있다.

`CONNECT` / `BREAK` / `1 → 2` / 존 이름 — **전부 불필요.**
붙었는지 떨어졌는지는 설명이 필요한 정보가 아니다.

#### 번역 4. 준비 카드는 **카드가 아니다**

준비(skill) 카드 6종은 존에 놓을 수 없다. 그런데 지금은 스윙 카드와 **똑같이 생겼고**,
`준비` / `스윙`이라는 글자로만 구분된다.

→ **준비는 카드가 아니라 원형 칩**으로 만든다.
네모난 것은 존에 놓고, 둥근 것은 놓을 수 없다. **형태가 규칙이다.**

#### 번역 5. 위력 = 카드의 **무게**

`power` 값(0/1/2/3)이 카드의 **두께와 재질**이 된다.
얇은 카드는 가볍게 놓이고, 두꺼운 카드는 **쿵 하고 놓인다**(모션·햅틱·사운드가 함께 무거워진다).

장타 카드는 "파워 +36"이라고 쓰지 않는다. **무겁다.**

### 2.2 텍스트 존재 심사 — 모든 글자가 통과해야 하는 3문

화면의 글자 하나하나에 아래를 묻는다. **하나라도 "예"면 남기고, 전부 "아니오"면 지운다.**

| 질문 | 예시 |
| --- | --- |
| **Q1. 고유명사인가?** (사람·팀·카드의 이름) | `#7 강한결`, `유상혁` |
| **Q2. 물리로 옮길 수 없는 추상 수량인가?** | 볼카운트, 아웃, 점수 |
| **Q3. 이 화면의 목적이 "비교하고 고르기"인가?** | 보상 3장 비교, 덱 열람 |

Q3이 핵심이다. **전투는 실행하는 화면이고, 보상·덱은 비교하는 화면이다.**
비교에는 이름이 필요하고, 실행에는 형태만 있으면 된다.

## 3. 카드 — "정타 노림"은 필요한가

### 3.1 직답

**전투 화면에서는 필요 없다. 덱·보상·도감 화면에서는 필요하다.**

근거는 §2.2 Q3이다.

| 화면 | 플레이어가 하는 일 | 이름 | 이유 |
| --- | --- | --- | --- |
| **전투** | 이 공에 어느 형태를 어디에 놓을지 **실행** | **불필요** | 형태·두께·글리프로 식별된다. 이름을 읽을 시간에 존을 본다 |
| **보상(드래프트)** | 3장을 **비교** | **필요** | 비교에는 지칭이 필요하다 |
| **덱 열람** | 내 덱을 **점검** | **필요** | 목록은 이름으로 읽는다 |
| **도감** | **학습** | **필요** | 배우는 화면 |

### 3.2 그런데 진짜 문제는 이름이 아니었다

현재 카드 1장이 들고 있는 텍스트 행을 세어 보면:

```
[준비/스윙]  [역할 · 축]  [이름]  [gives 칩들]  [needs 칩들]
[규칙 본문 1~3줄]  [강화 설명]  [연계/상충 사유]  [노트]  [플레이버]
```

**최대 9행.** 이름은 그중 **한 줄**이다.

> **"정타 노림"이 문제가 아니라, "정타 노림"이 9줄 중 하나라서 문제다.**
> 나머지 8줄을 형태로 옮기면 이름은 **유일한 한 줄**이 되고, 그때는 비용이 없다.

이름을 지우는 것은 답이 아니다. **이름만 남기는 것**이 답이다.

### 3.3 카드 해부 — 9행을 어디로 보내는가

| 현재 텍스트 행 | 어디로 | 물리 표현 |
| --- | --- | --- |
| `준비` / `스윙` 배지 | **형태** | 준비=원형 칩, 스윙=사각 카드 (§2.1 번역 4) |
| `역할 · 축` (정타·1존) | **형태** | 카드 외곽선 자체가 축(point/row/column/cross/all) |
| **이름** | **유지** | 전투에서는 2차(작게), 덱·보상에서는 1차 |
| `gives` 칩 (1존 커버, 파워 +36 …) | **형태 + 두께** | 커버=외곽선, 파워=두께, 정보=렌즈 노치, 진루=베이스 각인 |
| `needs` 칩 (아웃 지불, 주자) | **비용 표식** | 카드 아래 모서리의 **결손부**(이가 빠진 모양) = 무언가를 지불한다 |
| 규칙 본문 | **상세 시트** | 길게 누르면 원문 그대로 |
| 강화 `+` 설명 | **재질** | 강화 카드는 가장자리에 **금박 한 줄**. 상세에서 문장 |
| 연계 / 상충 사유 | **접합** | 연계=접합선 발광, 상충=모서리 어긋남(§2.1 번역 3) |
| 플레이버 | **삭제** | 도감에만 남긴다 |

### 3.5 이름의 자리 — 화면별 등급

| 화면 | 이름 표시 | 크기 |
| --- | --- | --- |
| 전투 손패 | **2차** — 카드 하단 작게 | `--t-micro` 12px |
| 전투 보드 위(배치됨) | **없음** | — |
| 길게 누르기 상세 | 1차 + 원문 규칙 전체 | `--t-h3` |
| 보상 드래프트 | **1차** | `--t-h3` 18px |
| 덱 열람 | 1차 | `--t-label` |
| 도감 | 1차 + 플레이버 | `--t-h3` |

### 3.6 이름을 처음 배우는 순간 — 인장

새 카드가 덱에 들어오는 순간(보상 확정) **1회만**, 카드 형태 위에 이름이 **인장처럼 찍히는**
0.5초 연출을 준다. 그 뒤로 전투에서는 형태만 봐도 떠오른다.

**이것이 튜토리얼을 대체한다.** 카드를 얻는 순간이 곧 학습 순간이다.

### 3.7 이름 자체의 품질 — 사용자 결정 필요

현재 16종 이름의 길이가 2자에서 **8자**(`히트앤드런 사인`)까지 흩어져 있어
목록에서 리듬이 깨진다. **3~5자로 고르는 것을 권하지만, 이름은 제품 정체성이므로
내가 임의로 바꾸지 않는다.** §14-3 결정 항목.

## 4. 9존 보드 — 덮기 · 쌓기 · 맞닿기

### 4.1 보드는 격자가 아니라 **판**이다

현재: 9개의 독립 버튼. 각 칸에 `IN·HIGH` / `LOW` / `비숙련` 3~4개 텍스트(§V12-UI-MASTER-SPEC §1.0.2).

바꿈: **하나의 판** 위에 9개의 자리. 칸 이름(`몸쪽 높음` 등)은 **위치가 곧 이름**이므로 삭제한다.
왼쪽이 몸쪽, 위가 높은 공 — 야구를 몰라도 **두 번만 보면 안다.**

### 4.2 읽기 등급 = 판의 **온도**

| 등급 | 표현 |
| --- | --- |
| 미사용 존 | 판이 **눌려 있다**(음각) + 차갑다 |
| 등급 0 (명암만) | 옅은 온기, 경계 흐림 |
| 등급 2 (구간) | 뚜렷한 온기 + 거친 입자 |
| 등급 4 (정확) | 밝은 온기 + 매끈함, 길게 누르면 수치 |

`확률 0` / `비숙련` / `코스 경향 · 확정 예고 아님` — **전부 삭제.**

### 4.3 배치 · 겹침 · 맞닿음

| 동작 | 물리 |
| --- | --- |
| 카드를 존으로 끌기 | 카드가 손에서 떠올라 판 위에 **내려앉는다.** 두꺼운 카드는 늦게·무겁게 |
| 덮기 | 카드가 해당 칸들을 **가린다.** 가려진 칸의 온기는 카드 테두리로 새어 나온다 |
| 겹치기 | 새 카드가 기존 더미 **위에** 앉는다. 더미 그림자가 깊어진다 |
| 맞닿기 | 인접하면 **모서리가 붙고 접합선이 빛난다** |
| 떨어짐 | 인접하지 않으면 그냥 떨어져 있다. **끊긴 것을 그릴 필요조차 없다** |
| 회수 | 카드가 손으로 되돌아간다. 정확히 역경로 |

### 4.3.1 시안

`design/v12/card-shape-language.png` 하단의 보드 데모가 덮기·맞닿음·떨어짐·두께·판의 온도를
한 장에 담고 있다. 글자는 카드 이름 3개뿐이다.

### 4.4 그래서 사라지는 것

`COVER n/9`, `PLACE CARDS`, `SWING ROUTE / 9ZONE`, `CONNECT n/m`, `BREAK`, `CONNECTED`,
`1 → 2`, `ROUTE LOCKED`, `PERFECT CONNECT`, `SWING ORDER`, `DRAG`, `MAIN`, 셀 좌표명 9종,
숙련도 라벨 9종 — **약 60개의 텍스트가 그릴 필요조차 없어진다.**

### 5.4 판정 · 결과 — 연출이 규칙을 가르친다

이 게임에서 연출은 **보상이자 교재**다. 호평받은 부분이므로 줄이지 않되, **인과를 반드시 보여준다.**

| 판정 | 화면이 반드시 보여줘야 하는 인과 |
| --- | --- |
| 적중(안타) | 공이 **덮인 칸 안으로** 들어오는 궤적 → 배트가 그 칸에서 만난다 |
| 헛스윙 | 공이 **덮이지 않은 칸을** 지나간다. 덮인 칸은 그 순간 **비어 있음이 보인다** |
| 한 칸 차이 | 공이 지나간 칸과 덮은 칸이 **나란히** 강조된다. "아깝다"가 장면으로 |
| 루킹 스트라이크 | 배트가 움직이지 않고 공이 판을 통과 |
| 볼 | 공이 판 **바깥**으로 지나간다. 판 경계가 그 순간 뚜렷해진다 |
| 파울 | 배트가 스치고 공이 판 밖으로 튄다 |
| 홈런 | 카메라가 공을 따라 나간다 (기존 유지) |

**"왜 실패했는지"를 문장으로 쓰지 않는다. 공이 어디로 갔는지 보여준다.**

| | |
| --- | --- |
| **삭제** | `REVEAL · SAME BATTER`, `{n}볼 {n}스트라이크 · {이름} 그대로 타석에`, `PLATE APPEARANCE COMPLETE`, 실패 원인 문장 |
| **남는 글자** | 판정어 1개(`안타`/`삼진`) + 다음 버튼 1개 |

### 5.5 보상(드래프트) — **여기서는 글자를 아낀다고 이득이 없다**

비교하는 화면이다(§2.2 Q3). 이름과 규칙이 **필요하다.**
대신 **비교 자체를 형태로** 만든다.

| 지금 | 바꿈 |
| --- | --- |
| 후보 3장 + 덱 진단 문장 + 변화량 문장 | 후보 3장이 **형태로** 나란히: 작고 두꺼운 것 / 길고 얇은 것 / 십자 |
| `범위 구성 · 역할 분포 · 준비:스윙 비율` 진단문 | **덱 커버 히트맵** — 내 덱 전체가 9존 중 어디를 얼마나 덮는지 한 장 |
| `이 카드를 넣으면 …가 해소됩니다` | 후보에 손을 올리면 **히트맵이 즉시 변한다.** 비어 있던 칸이 채워지는 게 보인다 |

> 덱 히트맵은 **"내가 어떤 야구를 하고 있는가"를 한 장으로 보여준다.** 문장 0개.

| | |
| --- | --- |
| **남는 글자** | 카드 이름 3 + 규칙 1줄 3 + `건너뛰기` |
| **수용 기준** | 문장 **1 이하**, 진단 문구 **0** |

### 5.6 시설

| 시설 | 지금 | 물리 |
| --- | --- | --- |
| 훈련(강화) | 카드 목록 + 강화 설명문 | 배팅 케이지. 카드를 티에 올리면 **금박이 입혀진다** |
| 라커룸(제거) | 목록 + 설명 | 사물함. 카드를 넣으면 **문이 닫힌다** |
| 장비 상점(유물) | 유물 3종 + 설명문 | 진열대 위 **물건 3개**. 집으면 손에 들린다 |
| 휴식 | `다음 경기 타격 기술 +8` | 벤치에 앉는다. 다음 경기 배지에 **불이 들어온다** |

| | |
| --- | --- |
| **남는 글자** | 대상 이름 + 효과 1줄 + 확정 버튼 |
| **수용 기준** | 화면당 문장 **1 이하** |

### 5.7 덱 · 도감

**읽는 화면이므로 글자를 허용한다.** 단 구조를 준다.

- 덱 화면 상단에 **덱 커버 히트맵** 1장 (§5.5).
- 카드는 **형태 그대로 정렬** — 같은 형태끼리 모이면 덱 구성이 한눈에 보인다.
- 도감은 학습 화면이다. 이름·규칙·플레이버·강화 **전부 표시**한다.
  전투에서 지운 문장들의 **집이 여기**다. 정보는 사라지지 않는다.

### 5.8 패배 · 승리 · 런 종료

| | |
| --- | --- |
| **지금** | 결과 문구 + 통계 |
| **물리** | **9존 히트맵 2장**: 내가 덮은 칸 / 투수가 실제로 던진 칸. 두 장이 어긋나 있으면 패배 이유가 **보인다** |
| | 그 아래 타임라인: 타석마다 한 칸, 색으로 결과 |
| **남는 글자** | 결과어 1 + 다시 시작 1 |
| **수용 기준** | 패배 원인을 **문장 없이** 알 수 있다 |

> 패배 화면은 "왜 졌는지 설명하는 화면"이 아니라 **"왜 졌는지 보이는 화면"**이다.

## 6. 학습 곡선 — 설명 없이 배우는 순서

가르치는 주체는 **문장이 아니라 사건**이다.

| 순서 | 개념 | 언제 | 무엇이 가르치나 |
| --- | --- | --- | --- |
| 1 | 존을 고른다 | 첫 타석 | 고스트 손 데모 0.6s (문장 0) |
| 2 | 카드가 칸을 덮는다 | 첫 배치 | **카드가 칸을 가리는 것 자체** |
| 3 | 덮은 칸에 오면 안타 | 첫 적중 | 공 궤적이 덮인 칸으로 들어가는 연출 |
| 4 | 안 덮으면 헛스윙 | 첫 실패 | 공이 빈 칸을 지나가는 연출 |
| 5 | 투수 HP를 깎는다 | 첫 적중 직후 | HP 바가 줄어드는 것을 **같은 화면에서** 본다 |
| 6 | 여러 장 = 넓지만 약하다 | 2장째 배치 | 쌓이는 두께 + 고스트 구간 축소 |
| 7 | 붙이면 조금 돌아온다 | 첫 맞닿음 | 접합선 발광 + 고스트 구간 증가 |
| 8 | 준비는 다르다 | 준비 칩 첫 보유 | 둥근 칩이 존에서 튕겨 나온다 |
| 9 | 읽기 등급 | 관찰 칩 첫 사용 | 판의 온도가 선명해진다 |
| 10 | 덱이 내 야구다 | 첫 보상 | 히트맵이 변하는 것을 본다 |

**1~5가 첫 타석 안에서 끝난다.** 6~7은 자연히 2장을 놓게 될 때. 8~10은 그 기능을 처음 만날 때.
**어느 단계에도 설명 모달이 없다.**

### 6.1 개념별 1회 데모

각 개념은 **처음 가능해진 순간** 0.5~0.8초 데모를 1회 재생한다(문장 0).
`b.turn<=2` 시간 게이트를 **개념별 1회 플래그**로 대체한다.

## 7. 사운드 · 햅틱 (전 화면 공통)

물리 번역은 **소리로 완성된다.** 무거운 카드가 소리도 무거워야 물리가 성립한다.

| 사건 | 소리 | 햅틱 |
| --- | --- | --- |
| 얇은 카드 배치 | 가벼운 종이 (3kHz, 짧음) | 8ms |
| 두꺼운 카드 배치 | **낮고 묵직한 나무** (800Hz + 저역) | 24ms |
| 겹쳐 쌓기 | 두 번째 층부터 **둔탁해진다** | 18ms |
| 맞닿음 | 금속 접합 상승 2음 | `[9,18,9]` |
| 회수 | 역재생 | 8ms |
| 준비 칩 튕김 | 단단한 거부음 | 40ms |
| 지도 이동 | 버스 정차음 | 12ms |
| 보상 확정(인장) | 도장 찍히는 소리 | 30ms |

UI음 2~4kHz, -18dB 이하. 판정 연출의 저역과 **주파수대를 분리**한다.

### 10.1 순서의 이유

- **P0 없이 P2~P6을 하면 전부 `!important`가 된다.**
- **P1이 P2보다 먼저인 이유**: 어차피 지울 글자를 키우는 낭비 같지만, 키워 봐야
  **무엇을 지울지 보인다.** 6px로는 무엇이 중복인지조차 안 보인다.
- **P7(학습)이 마지막인 이유**: 시끄러운 화면에서 데모를 틀면 묻힌다.
- **P2(카드)가 P3(보드)보다 먼저인 이유**: 보드의 "덮기"는 **카드가 형태를 가진 뒤에만** 성립한다.

### 10.2 아트 작업과의 관계

`HANDOFF.md`의 VISUAL REBOOT(타자·투수 픽셀아트)는 **이 로드맵과 병렬**이다.
- 시각 방향 **A(타자 시점)**를 고르면 아트 리부트가 **선행 조건**이 된다.
- **B(전광판)** 를 고르면 아트 의존도가 낮아 병렬 진행이 쉽다.
- **C(덱 테이블)** 는 투수 초상 전용 아트가 필요하다.

§14-1의 방향 선택이 아트 일정까지 결정한다.

### 11.1 고위험 5

1. **P0 레이어 래핑의 우선순위 역전** — 픽셀 비교를 완료 조건으로.
2. **테스트 단언 선이전** — 순서를 뒤집으면 회귀 감지 불가.
3. **형태 기반 히트 영역** — 세로/가로/십자 카드의 터치 영역이 서로 다르다. 44px 최소 보장 필요.
4. **정보 소실** — 지운 문장마다 3채널표에 행이 있어야 한다. 없으면 삭제 보류.
5. **단계 사이 톤 불일치** — P3까지 끝난 전투와 P5 이전의 지도가 다른 게임처럼 보인다.
