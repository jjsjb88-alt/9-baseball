## 0. 검수 결론

텍스트 밀도를 줄이고 행동과 결과를 가까이 두는 방향은 유지한다.
그러나 '카드가 물리적으로 맞닿으면 연결된다', 'shape가 실제 커버다', '피해 배율이 예상 HP 피해다'라는
초안의 설명은 실제 엔진과 다르므로 교체한다. 모양만으로 초보가 규칙을 이해한다는 주장도 검증할 가설이다.

범위는 **타이틀·지도·전투·판정·보상·시설·덱/도감·패배/승리** 전체다.
게임 방식, 엔진 확률·피해·카드 효과·런 구조는 이번 기획에서 바꾸지 않는다.
아트 품질은 VISUAL REBOOT의 독립 완료 기준을 유지한다.

## 1. 제품 문장과 완료 목표

> 투수의 의도를 읽고, 9존 위에 카드를 순서대로 배치해 하나의 스윙을 설계하고,
> 투수를 무너뜨리는 야구 덱빌딩 로그라이트.

| 기준 | 확인 방법 |
| --- | --- |
| 처음 보는 사람이 조작을 시작할 수 있다 | 신규 5명 중 4명이 도움 없이 첫 배치. 시간·막힌 지점 기록 |
| 글자가 읽힌다 | 프로젝트 하한 12px, 본문 15px 권장. 실제 합성 대비·200% 확대·실기기 확인 |
| 지금 결정할 일을 안다 | 상태별 질문과 실제 행동으로 확인. 정지 시안 점수로 합격시키지 않는다 |
| 선택과 결과를 함께 본다 | 보드·손패·실행 버튼·현재 HP/효율이 같은 조작 맥락에 있다 |
| 정보가 정확하다 | 커버·순서·배율·공개 정보 경계가 엔진과 일치 |
| 입력이 즉시 반응한다 | 시각 반응 시작 ≤100ms. 햅틱·소리는 설정과 지원 여부에 따른 보조 |
| 회귀를 발견할 수 있다 | 정적·브라우저·의미·사람 검사를 분리하고 근거를 남긴다 |

첫 경기 승률·완주율은 관찰한다. UI 기획만으로 난이도 문제가 해결됐다고 결론 내리지 않는다.

## 2. 실제 규칙을 보이게 한다

### 2.1 표현과 데이터 계약

| 표현 | 단일 근거 | 보존할 정보 |
| --- | --- | --- |
| 커버 = 켜진 칸 | coverageAt / previewV10Stack의 coverage | shape는 기본 분류일 뿐. 위치·코스 조정·성장에 따른 실제 셀 사용 |
| 여러 장 = 카드 소비·효율 변화 | stackPlan.cardCount / damageRate | 중복 커버는 중복 집계하지 않음. 추가 카드가 새 칸을 늘리지 않을 수도 있음 |
| 이어치기 = 순서대로 기준 존 연결 | stackPlan.steps / links | 메인 ① 고정, 지원 ②~④ 순서. 연속 aimZone의 동일/8방향 인접 |
| 준비 = 구분되는 실루엣 | CARDS의 type / cardProblem | 이름·사용 조건·준비 잔여 횟수·발동 경로 유지 |
| 장타 성향 = 무게감 | cardPower(entry) | 강화 포함 -1~4. HP 피해량과 다른 값이며 지원 효과/파워는 합산 발동하지 않음 |

**커버와 연결은 다르다.** 커버가 겹치거나 카드 모서리가 닿아도 연결되지 않을 수 있다.
0부터 센 존 0→4→8은 2연결, 0→8→4는 1연결이다. 4→4도 연결이다.
그래서 순번·기준 존·연결선을 남긴다.

### 2.2 효율과 HP 피해를 분리한다

damageRate는 **HP 피해 배율**이며 다음 투구에서 깎일 HP가 아니다.
실제 피해는 판정·안타 종류·정확 적중·유물·반올림의 영향을 받는다.
첫 프로토타입은 **현재 HP와 별도의 피해 효율 %**를 보드 가까이 표시한다.
HP 바 위에 확정 피해처럼 깎일 구간을 그리지 않는다.

예상 HP 범위는 공개 정보로 산출한 범위와 실제 결과 계산의 일치가 입증된 뒤 별도 검수한다.
pending.zone·숨은 난수·낮은 읽기 등급의 정확 확률을 화면·ARIA·소리로 누설하지 않는다.
같은 공개 정보라면 같은 미리보기를 보여야 한다.

### 2.3 예외·공개 정보

- 읽기 등급은 **0 / 1 / 2**다. 관찰 점수 임계값 **2 / 4**와 다르다.
- 등급 0은 허용된 3단 음영, 1은 구간, 2는 정확 수치다. information.js의 공개 범위 계약을 유지한다.
- 등급 0의 낮은 음영을 '절대 안 던지는 존'으로 표현하지 않는다.
- 희생 번트는 **커버 적중=안타의 예외**다. 아웃 비용·2스트라이크 파울 위험을 표시한다.
- BASIC·번트·기다림의 스택 제한, 메인과 지원의 역할 차이를 유지한다.

### 2.4 텍스트 삭제 기준

장식 헤더와 중복 문장을 먼저 줄인다. 이름·비용·조건·오류·실패 원인은 삭제 목표가 아니다.
전투도 비교하고 결정하는 화면이다. 형태만으로 16종이 구분된다고 가정하지 않는다.
정보 상세는 명시적 버튼·키보드로도 열 수 있어야 하며 길게 누르기는 보조 경로다.

## 3. 카드

### 3.1 이름과 상세

손패의 카드 이름은 **유지**한다. 최소 12px, 선택/상세/보상에서는 15~18px를 우선한다.
보드에는 순번 토큰과 선택 시 이름, 상세에는 기존 cardText·강화·조건을 제공한다.
이름 재명명은 이번 검수에서 하지 않는다.

### 3.2 형태 사양 — 기본 분류표

| 카드 | 기본 shape | 기본 power | 별도로 표현할 것 |
| --- | --- | ---: | --- |
| 정타 노림 place | point | 0 | 메인 정확 적중 HP 압박 +50% 조건 |
| 밀어치기 strike | column | 0 | 바깥쪽 타구 질 특성 |
| 당겨 넘기기 slug | point | 2 | 장타 성향 |
| 주자 연결 rally | row | 0 | 메인 적중 시 기존 주자 진루 |
| 희생 번트 bunt | all | 0 | 희생/파울·아웃 비용, 안타 보장 예외 |
| 갭 공략 finisher | row | 1 | 장타 성향 |
| 커트 스윙 defend | cross | -1 | 적중 단타·범위 밖 파울 생존 |
| 존 봉쇄 wall | cross | 0 | 시그니처 표시와 생존 효과 부재 |
| 라인드라이브 laser | column | 1 | 시그니처·장타 성향 |
| 끝장 승부 commit | point | 3 | 강화 시 cardPower=4 |

십자는 모서리 3칸·변 4칸·중앙 5칸이다. 코스 조정과 성장은 범위를 다시 바꾼다.
따라서 손패의 형태는 분류 힌트, 배치 미리보기는 **계산된 셀**이다.
강화는 파워 또는 특수 효과를 바꾸므로 금테 하나로 효과 설명을 대체하지 않는다.
지원 카드의 장타·진루·정타 효과가 발동하는 것처럼 표시하지 않는다.

### 3.3 준비 카드 6종

setup=집중, watch=드로우, scout=공개 단서+드로우, lure=범위 확장,
flow=주자 진루 조건, calm=파울 생존+드로우다. 강화 전후 상세를 보존한다.

원형 실루엣은 프로토타입 후보지만 **44px 이상의 일정한 조작 영역과 이름을 유지**한다.
존에 끌었다가 거부당해야 조작법을 배우는 구조로 만들지 않는다.
준비 횟수와 조건 불충족 이유를 화면·접근 가능한 이름에서 확인할 수 있어야 한다.

### 3.4 비교·시너지

덱의 relationsFor 기반 시너지와 전투의 V11 순서 링크는 별개다.
연계 문구를 모두 하나의 접합선으로 합치지 않는다.
새 카드 획득 인장은 보조 연출이며 반복 확인 가능한 상세·도움을 대체하지 않는다.

## 4. 9존 보드

### 4.1 구조

정면의 일정한 3×3 셀을 사용한다. 원근은 경기장에 적용하고 입력판에는 적용하지 않는다.
몸쪽/바깥쪽·높낮이는 짧은 범례와 접근 가능한 이름으로 확인한다.
셀 좌표 1~9와 배치 순번 ①~④는 다른 모양으로 구분한다.

### 4.2 레이어

읽기 음영 → 반투명 커버/테두리 → 순번·기준 존 → 순서 링크.
어느 카드도 분포·순번·현재 선택을 불투명하게 가리지 않는다.
'안 던지는 존'과 '배치할 수 없는 존'을 구별하며 정보 표시만으로 입력을 금지하지 않는다.

### 4.3 조작

| 동작 | 계약 |
| --- | --- |
| 배치 | 카드 탭→존 탭 기본. 드래그·키보드도 동일 결과 |
| 중복 존 | 순번을 펼쳐 개별 선택·회수 가능. 동일 존 링크 표시 |
| 재정렬 | 메인 고정·지원만 이동. 앞/뒤 버튼 대안 보존 |
| 편집/회수 | 편집 선택과 삭제를 구분. 명시적인 회수 버튼 제공 |
| 확정 | 기존 1회 확정·중복 실행 잠금 유지. 추가 2단 확인을 도입하지 않음 |

### 4.4 남길 정보

순번, 메인/지원 구별, 현재 HP, 피해 효율, 카드 소비, 발동 조건과 오류 이유를 남긴다.
COVER n/9는 실제 셀이 명확히 읽히는지 검증한 뒤 시각적으로 생략할 수 있다.
텍스트를 지우기 전에 동등한 정보와 조작 검사를 확보한다.

## 5. 화면 전수 설계

| 화면 | 방향 | 반드시 보존할 정보·행동 |
| --- | --- | --- |
| 타이틀 | 게임 장면과 새 런/이어하기/연습·고급 | 저장 상태, 접근 가능한 메뉴, 실패·복구 경로 |
| 지도 | 실제 연결된 길과 유형별 노드 | 선택 전 종류·위험·보상 비교, 선택 상세, 세로 스크롤 |
| 전투 | 보드·손패·HP/효율·실행 버튼의 가까운 배치 | 읽기·비용·순서·메인/지원·회수·확정 |
| 판정 | 공개된 실제 공 위치·커버·결과를 이어 보여줌 | 안타/헛스윙/파울/희생/볼/삼진/홈런 차이, 다음 공과 다음 타자 |
| 보상 | 후보를 같은 기준으로 비교 | 이름·핵심 효과·조건·강화 상태·선택/건너뛰기 |
| 시설 | 행동을 물건·공간으로 표현 | 대상·효과/비용·확정·취소, 선택 불가 이유 |
| 덱/도감 | 형태별 정렬과 상세 | 이름·규칙·시너지·강화·플레이버, 언제든 재확인 |
| 패배/승리 | 실제 사건 순서와 결과 | 종료 이유·다시 시작·핵심 비용, 집계만으로 원인 단정 금지 |

### 5.1 지도

실루엣만으로 초보가 시설 종류·위험을 안다고 가정하지 않는다.
짧은 유형 이름과 선택 상세를 유지하고 반복 설명을 줄인다.
노드 크기나 색은 보조 표현이다. 위험·보상을 비교할 수 있어야 한다.

### 5.2 보상·덱

카드는 aimZone을 자유롭게 바꿀 수 있으므로 **배치 가정 없는 덱의 위치별 커버 히트맵은 정의되지 않는다.**
첫 구현은 shape별 구성·준비/스윙·역할·강화 전후 비교를 쓴다.
히트맵은 배치 정책과 분모를 명시하고 서로 다른 덱을 구별하는지 검증한 뒤 도입한다.

### 5.3 판정·종료

미적중은 항상 헛스윙이 아니며 파울 등이 가능하다. 번트는 덮인 칸에서도 희생/파울이다.
실제 revealed/lastCombat 값만 사용한다. 순서별 커버·투구·카드 소비·HP 결과를 연결해 보여준다.
실패 이유를 짧게 다시 확인할 수 있게 한다. 누적 히트맵 두 장의 차이를 곧 패배 원인이라고 단정하지 않는다.
필요한 런 전체 기록이 없으면 새 기록 계약·용량·저장 호환 검증을 먼저 정의한다.

## 6. 학습 곡선

첫 배치 → 커버 → 실제 적중/실패 → HP 변화 → 추가 카드 비용 → 순서 링크 →
준비 조건 → 읽기 정보 → 덱 비교 순으로 실제 발생한 사건에서 가르친다.
첫 타석에 성공·실패를 모두 경험한다고 보장하지 않는다.

짧은 데모와 이름/한 줄 도움을 함께 검증한다. 모달 강제는 피하되 설명 접근은 남긴다.
온보딩은 P2~P6 각 단계의 완료 조건이며 P7까지 미루지 않는다.
버전 있는 UI 설정을 우선 검토하고 게임 세이브를 임의로 확장하지 않는다.
신규 프로필은 미학습, 기존 프로필은 명시적 이관, 스킵/재생/저장 실패를 구분한다.

## 7. 사운드·햅틱

시각 피드백은 필수, 소리·햅틱은 사용자 설정과 브라우저 지원에 따른 보조다.
음소거·진동 미지원·reduced-motion에서도 같은 정보를 얻는다.
무게감은 장타 성향의 표현이며 확정 피해의 약속이 아니다.
기존 audio.js/haptics 실패가 전투를 막지 않는 계약과 판정 연출을 유지한다.

## 8. 접근성·입력

- 카드 탭→존 탭, 명시적 상세 버튼, 회수·앞/뒤 버튼, 키보드 대안을 보존한다.
- 손패의 native 가로 스크롤과 문서 세로 스크롤을 드래그가 가로채지 않는다.
- 실루엣과 실제 히트 영역을 분리한다. 44×44 CSS px를 프로젝트 기준으로 삼고 겹침을 검사한다.
- 색·모션만으로 의미를 전달하지 않는다. 이름·상태·조건은 ARIA에도 같은 공개 정보 수준으로 제공한다.
- 본문 대비는 합성된 배경·opacity·비활성 상태까지 검증한다. 토큰 색끼리의 계산만으로 합격시키지 않는다.
- 200% 확대, 키보드 포커스, 스크린리더, reduced-motion에서 핵심 플로우를 검증한다.

## 9. 측정과 합격 기준

### 9.1 사람

신규 5명의 첫 배치 시간(목표 20초 이내), 막힌 지점, 무효 입력을 기록한다.
의도적 회수·전략 변경은 오조작으로 세지 않는다. 경기 완주율은 baseline부터 측정한다.
3문답: 추가 카드의 비용/커버/효율, 순서가 연결을 바꾸는 이유, 방금 결과의 실제 원인.
도움말 열람 감소 자체를 성공으로 보지 않는다.

### 9.2 화면 예산

기본 상태의 설계 목표: 타이틀 6, 지도 미선택 6, 전투 28, 판정 2, 보상 12, 시설 8 텍스트 요소.
덱·도감은 상한 없음. **오류·조건·접근성·선택 상세·효과 비교는 예산 때문에 삭제하지 않는다.**
텍스트 노드 수와 사용자가 읽어야 하는 정보량을 같은 것으로 취급하지 않는다.

### 9.3 검증 분리

정적 검사는 신규 UI 토큰·중복·예외 목록을 감시한다.
브라우저 검사는 실제 글자·대비·조작 영역·넘침을 확인한다.
의미 검사는 엔진/공개 정보/입력/저장 계약을 확인한다.
사람 검사는 이해도와 재미를 확인한다. 어느 하나도 나머지를 대신하지 않는다.
