# 9ZONE SHOWDOWN 자율 개발 한 바퀴

## ① 합격 기준 (한 문장)

이걸 다른 사람이 봤을 때도 퀄리티가 떨어지지 않는가? 통과 못 하면 커밋하지 마.

## ② 먼저 읽을 문서

1. `docs/feedback/INBOX.md` — 사용자의 실제 지시
   - 어디까지 읽을지: 문서 전체. 짧다. **여기 있는 항목 하나만 골라서 한다.**
2. `docs/STATUS.md` — 지금 무엇이 되어 있고 무엇이 미검증인지
   - 어디까지 읽을지: 맨 위 "현재 상태" 절 하나. 그 아래 "과거 상태"는 역사이며 지침이 아니다.
3. `HANDOFF.md` — 최신 인수인계서
   - 어디까지 읽을지: 맨 위 "최우선 인수인계" 절 하나. 80KB 전체를 읽지 마라.
4. `docs/DECK.md` — 덱·보상·강화·유물·읽기 등급의 현행 계약
   - 어디까지 읽을지: 손댈 영역의 절만. §1의 근거 표는 새 연계를 만들기 전에 반드시 읽는다.
5. `docs/DUEL.md` — 전투 규칙
   - 어디까지 읽을지: 판정·커버·성장을 건드릴 때만, 해당 절만.

## ③ 규칙과 근거

- 규칙: 작업이 완료되면 다음 새 세션이 일을 진행할 수 있도록 최신 인수인계서를 작성할 것.
  - 왜: 제대로 작성하지 않으면 기존 작업의 흐름을 잃고 엉뚱한 방향으로 움직인다.
- 규칙: 사용자 작업이 실패하면 현재 보이는 화면에 접근 가능한 오류를 표시하고, 입력을 보존한 재시도 경로를 회귀 검사로 고정할 것.
  - 왜: 숨겨진 화면의 메시지는 실패를 무반응처럼 보이게 하며, CORE TEST 저장과 JSON 내보내기에서 같은 고장이 반복됐다.
- 규칙: **`git push`와 배포를 하지 마라.** 커밋은 현재 브랜치에 남기고 원격에는 올리지 않는다.
  - 왜: `main`에 올라가면 CI가 곧바로 공개 사이트에 배포한다. 무엇을 공개할지는 사용자가 정한다.
- 규칙: **INBOX가 비어 있으면 새 작업을 지어내지 마라.** `STATUS.md`의 "다음 작업"을 보고,
  거기에도 지금 할 수 있는 것이 없으면 **아무것도 커밋하지 말고** 그 사실만 보고하고 끝낸다.
  - 왜: 2026-09-01~02에 빈 지시문으로 루프를 돌려 실행 불가능한 QA를 14회 재시도했다.
    전체 커밋 91개 중 26개가 실질 변경 없는 공회전이었다. 할 일이 없을 때 멈추는 것이 정상 동작이다.
- 규칙: 실행할 수 없는 검증이 있으면 재시도하지 말고, 무엇이 없어서 못 했는지 한 번만 적고 다음으로 넘어가라.
  - 왜: 같은 실패를 반복 기록하는 것은 진행이 아니다.

## ④ 한 바퀴 도는 순서

읽기 → 하나만 만들기 → 실행해서 눈으로 확인 → 커밋 → `STATUS.md` 갱신

## ⑤ 커밋 순서 규칙

검사를 통과하면, 화면을 보기 **전에** 일단 커밋한다.

한 바퀴는 도중에 멈출 수 있다. 멈춘 자리에 커밋이 없으면 그 작업은 사라진다. 화면 확인 뒤 수정이 생기면 다시 검사하고 후속 커밋을 남긴다. `STATUS.md`와 `HANDOFF.md` 갱신도 커밋되어야 한 바퀴가 끝난다.

## ⑥ 검사와 QA

- 화면이 있는 것을 만들면, 실행해서 스크린샷을 찍고 그 이미지를 직접 읽어라. 코드가 도는 것과 화면이 괜찮은 건 다른 문제다.
- 같은 지적이 두 번 나오면 규칙으로 올리고, 기계가 잴 수 있는 규칙이면 검사로 만들어 둬라. 한 번 겪은 고장을 두 번 겪지 않는다.
